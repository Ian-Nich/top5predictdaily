# top5predictdaily — Backend Handoff Notes

Goal: scan the market each morning for stocks under $20, rank them by
likelihood of gapping up at the 9:30am open, and surface the top 5. Originally
a 4-ticker "quantum stocks" basket demo; rebuilt into a general market
scanner + ranker. Owner plans to paper trade the daily top-5 list on Webull
and feed real outcomes back into retraining.

## Repo layout

```

│   ├── scraper.py               Per-ticker price/news data pull
```

## Pipeline (live path)

```
screener.get_universe()          -> live Yahoo screen, price < $20, has momentum
        |                           (NO FALLBACK - raises if screen fails or too few candidates)
        v
scraper.try_live_pull()          -> per-ticker premarket price/volume + real news headlines
        |                           (VADER sentiment on live headlines; per-ticker fetch errors
        |                            are skipped individually, not fatal to the whole batch)
        v
feature_engineering.build_features() -> list of per-ticker feature dicts + shared
        |                                universe/macro context (qqq change, % of
        |                                universe green)
        v
predictor.rank_top_picks()       -> scores every candidate with model.pkl, filters to
        |                           UP + price<$20 + expected_move >= threshold, ranks,
        |                           returns top N (NO rule-based fallback - raises
        |                           ModelUnavailableError if model.pkl is missing/broken)
        v
explainer.build_explanation()    -> one sentence per pick
        v
app.py's /api/refresh (POST)     -> assembles all of the above, logs picks to
                                     data/picks_log.csv, returns JSON to frontend
```

`train_model.py` and `build_watchlist.py` are **offline/periodic** jobs, not part of
the live request path - run them manually, not on every refresh.

## Key design decisions (and why)

- **Per-ticker ranking, not basket-averaging.** The original starter averaged
  features across a fixed 4-ticker basket into one score. That doesn't work for
  "rank N candidates, take top 5" - `feature_engineering.py` now returns one
  feature vector per ticker, and `predictor.py` scores each independently.

- **No fallback, anywhere, by explicit owner request.** If live data pull fails,
  the screener fails, or there's no trained model, the relevant function
  *raises* rather than silently substituting stale/sample data or a cruder
  scoring method. `app.py` catches these and returns a clean HTTP error (502
  for data-pull failures, 503 for `ModelUnavailableError`) - never a degraded
  "looks normal but isn't" response. The one deliberate exception: inside a
  batch pull, one ticker's individual fetch error is skipped rather than
  aborting the whole batch - that's a judgment call the owner accepted, not an
  oversight.

- **Premarket-aware pricing.** `scraper.py` prefers `preMarketPrice`/
  `preMarketChangePercent` when available, since the target is the *open* gap,
  not intraday movement.

- **News is live-only - there's a real train/serve mismatch, by necessity.**
  Free sources don't give clean historical per-date news archives, so
  `train_model.py` fills `news_sentiment`/`news_count` with neutral
  placeholders for every training row (confirmed via feature importances:
  both are exactly 0.0 importance - the model correctly learned to ignore a
  zero-variance feature). Live predictions DO get real sentiment via
  yfinance's `Ticker.news` + VADER. This means the live model has access to a
  signal it never saw in training - a known, accepted limitation, not a bug.

- **Liquidity floor, not just a price cap.** `build_watchlist.py` requires
  avg volume >= 300,000/day (tunable via `MIN_AVG_VOLUME`) in addition to
  price < $20. An illiquid name is both noisy training data and not something
  actually tradeable on Webull anyway.

- **screener.py vs build_watchlist.py are different jobs.** `screener.py` is
  the live daily scan used by `/api/refresh`. `build_watchlist.py` is a
  one-off/periodic (weekly/monthly) job that rebuilds `data/watchlist.txt`,
  a much broader universe used by `train_model.py` for backtesting. Don't
  merge these - they answer different questions ("what should I trade
  today" vs "what should the model learn from").

- **The label and the live filter threshold must stay in sync.**
  `train_model.py`'s `GAP_THRESHOLD_PCT` (currently **3.0**) defines what
  counts as a "win" during training. `predictor.py`'s `rank_top_picks()`
  `min_expected_move_pct` default (currently **3.0**) is what actually filters
  the live top-5 list. These were out of sync once already (model retrained
  at 3% while the live filter was still checking 5%) - if either changes,
  change both.

## Current model status (best run so far)

- Universe: ~1,814 tickers from `build_watchlist.py` (price < $20, avg volume >= 300k)
- Label: next day's open >= 3% above today's close
- Latest run: 322,879 train rows / 81,684 test rows, positive rate 6.5% (train) / 6.2% (test)
- **The metric that matters for this app** (not the classification_report's
  default 0.5-threshold precision/recall - that's the wrong lens for a
  ranking task): `evaluate_top_k_precision()` in `train_model.py`, which
  simulates "take the top 5 by score each day, check if they actually hit":
  - **Precision@5 = 0.326** (5.3x the 6.2% base rate)
  - **39 of 46 test days (85%) had at least one correct pick in the top 5**
- Feature importances are `volatility`-dominated (~0.55) across every run so
  far, with `universe_positive_ratio` (~0.18), `qqq_change_pct` and
  `relative_volume` moderate, and `volume_spike`/`news_sentiment`/
  `news_count` at ~0. Open question, not yet investigated: is the model
  mostly finding "already-jumpy stocks" (which are more likely to have *any*
  big move) rather than genuinely predicting *direction*? Worth probing
  before trusting this further - e.g. check whether high-`volatility` picks
  that *miss* are gapping down as often as up.
- History: same pipeline at a 5% threshold (fewer, larger moves) got
  Precision@5=0.278 at 9.7x base rate, 34/46 days with a hit. The 3%
  version has lower "x base rate" (ratios shrink when the base rate itself
  grows faster than precision does) but higher raw precision and more
  consistent daily coverage - a better fit for the owner's stated
  preference for more frequent, smaller, more reliable wins over rarer big ones.

## Bugs already found and fixed (don't reintroduce these)

- `model.predict_proba(...)` returns `numpy.float32`, which FastAPI can't
  JSON-serialize. Fixed by casting to native `float` immediately in
  `predictor.score_ticker()`, before any further arithmetic.
- This yfinance version (1.5.1) defaults `multi_level_index=True`, so even a
  **single**-ticker `yf.download()` call returns MultiIndex columns unless you
  pass `multi_level_index=False` explicitly. Confirmed via yfinance's own
  source (`multi.py`): multi-ticker downloads are ALWAYS MultiIndex regardless
  of that flag - only the single-ticker case gets flattened.
- `pandas.Series.astype(str)` on an object-dtype column does **not** convert
  `NaN` to the string `'nan'` in this environment - it silently leaves a real
  float mixed into otherwise-string data. This crashed `build_watchlist.py`'s
  `sorted(set(...))` call on a blank-symbol row in Nasdaq's real symbol file.
  Fixed with `.dropna()` before building the ticker-symbol set.

## Untested against live services (build sandbox had no network access to Yahoo Finance or nasdaqtrader.com)

- `screener.py`'s live `yf.screen()` / `EquityQuery` call
- `scraper.py`'s premarket `.info` fields and `Ticker.news` article schema
  (defensively coded with fallbacks/`.get()`, but field names/shapes not
  confirmed against a real response)
- `build_watchlist.py`'s Nasdaq symbol-file fetch and chunked yfinance
  pricing (parsing/filtering logic itself was unit-tested against synthetic
  data matching the documented formats; the live HTTP calls were not)

All of the above have run successfully against real data since (per the
owner's actual training runs), so they're now validated in practice - just
noting this was written blind to live responses, in case something about
those sources changes shape again later.

## Next steps (in order)

1. **Refactor `app.py` to be fully organized around the top-5-daily goal,
   not the legacy basket shape.** Right now it still carries
   `/api/data`, `/api/features`, and `/api/predict` from the original
   4-ticker starter (useful for offline testing against
   `sample_market_data.json`, but not the product). Decide whether to keep
   these as dev/test-only endpoints or retire them, and make
   `/api/refresh` (or a renamed equivalent) the one clearly-primary endpoint
   for "run the whole pipeline and give me today's top 5."

2. **Wire this into an actual daily routine.** Something that runs before
   9:30am ET, calls the refresh pipeline, and presents the top 5 in time to
   act on them - manually paper-trading the results on Webull to start.
   Doesn't need to be fully automated yet; a simple "run this script, read
   the output over coffee" workflow is a fine first version.

3. **Close the feedback loop.** `app.py` already writes every top-5 call to
   `data/picks_log.csv` with an `actual_gap_pct` column left blank
   specifically for this. What's missing: a process to fill that column in
   (e.g. a script that pulls each logged ticker's actual next-day open via
   yfinance and writes the real result back), and a way to fold that
   growing set of real, live outcomes into future retraining runs -
   this is the actual mechanism for "tie in whatever results I get to make
   this more accurate" that the owner asked for. Paper-trading results from
   step 2 are the first source of that real-world feedback.
